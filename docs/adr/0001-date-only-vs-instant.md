# ADR 0001 — Date-only values never travel through UTC

- **Status:** Accepted
- **Date:** 2026-08-06
- **Supersedes:** the ad-hoc `toISOString().slice(0, 10)` convention used in
  the scaffold and nine flagship pages

## Context

The app exchanges two different kinds of date with the API, and JavaScript's
`Date` conflates them:

| Kind | Wire format | Examples |
| --- | --- | --- |
| **date-only** — a calendar day, no time, no zone | `YYYY-MM-DD` | licence expiry, work-order due date, warranty end, calibration due |
| **instant** — a specific moment | full ISO 8601 | departure time, bag scan, release time |

`p-datepicker` binds to a `Date`. For a date-only field that `Date` is local
midnight, and the original code serialized it with `toISOString()`:

```ts
// TZ=Asia/Dhaka (UTC+6)
new Date(2026, 7, 6).toISOString().slice(0, 10);  // '2026-08-05'  ← a day early
```

The reverse, `new Date('2026-08-06')`, parses as UTC **midnight** per the ECMA
spec, so it renders as the 5th for every user west of UTC:

```ts
// TZ=America/New_York (UTC-4)
new Date('2026-08-06').toLocaleDateString();      // '8/5/2026'    ← a day early
```

So writes were wrong east of UTC and reads were wrong west of it. Both are
correct only in UTC itself, which is why the defect survived review — and why
it would have surfaced as scattered, unreproducible "the date is off by one"
reports from users in different regions.

In an aviation ERP this is not cosmetic. Airworthiness directives, medical
certificates and calibration intervals are compliance dates; a systematic
one-day error in either direction is an audit finding.

## Decision

`src/app/core/utils/date.util.ts` owns the conversion, and nothing else
performs it:

- `toDateOnly(date)` — serializes from **local** `getFullYear`/`getMonth`/
  `getDate`, never `toISOString`.
- `fromDateOnly(value)` — parses `YYYY-MM-DD` to **local** midnight; anything
  else is treated as an instant.
- `toRequiredDateOnly(date, fieldName)` — the same, typed as `string` for
  fields the form marks required, throwing with the field name rather than
  writing `null` into a NOT NULL column.
- `toInstant(date)` — `toISOString()`, for values that really are moments.
- `formatDate` / `formatDateTime` — display, without the UTC shift.
- `daysUntil(value)` — whole calendar days, midnight to midnight, so "expires
  today" is `0` rather than a fraction of a day in the past.

**Rule:** `toISOString()` may only be called on an instant. A date-only field
goes through `toDateOnly` / `fromDateOnly`. `new Date(someDateOnlyString)` is
a bug.

## Consequences

- Consistent calendar days regardless of where the user is.
- One place to change if the API ever moves to a different date encoding.
- `daysUntil` returning `number | null` forces call sites to decide what an
  absent date means, instead of silently comparing against `NaN`.
- `toRequiredDateOnly` throws on a state that should be unreachable. That is
  intentional: the alternative was a `!` non-null assertion, which threw a
  bare `TypeError` in exactly the same case with no indication of which field.
- Existing rows written by the old code are already skewed. There is no way
  to distinguish them from correct rows after the fact, so if any real data
  was captured against the mock backend it should be treated as suspect. The
  seeded demo data is regenerated by "Reset Demo Data".
